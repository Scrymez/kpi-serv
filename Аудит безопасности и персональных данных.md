# Аудит безопасности и персональных данных

Дата аудита: 2026-05-05

## Область проверки

Проверены Obsidian/Markdown-файлы проекта, Laravel backend, Vue frontend, маршруты API, авторизация, обработка файлов, импорт/экспорт Excel, настройки окружения и подготовка проекта к публикации в GitHub.

## Персональные данные в системе

Система обрабатывает:

- ФИО учеников, учителей и сотрудников;
- класс, возраст, предмет и роль пользователя;
- логины и временные пароли при создании/импорте;
- результаты олимпиад, дипломы PDF/изображения;
- KPI-баллы, рейтинги, апелляции;
- служебные токены авторизации Sanctum;
- Gemini API ключ.

## Критичные риски

### 1. Дефолтный администратор `admin / admin123`

В `ЗАПУСК.md` и `backend/database/seeders/DatabaseSeeder.php` указан пароль администратора `admin123`. Если такой пользователь попадет в production без смены пароля, система будет скомпрометирована.

Рекомендации:

- требовать смену пароля при первом входе;
- генерировать первичный пароль через переменную окружения;
- запретить production seed с известным паролем;
- добавить политику сложности пароля.

### 2. Экспорт и возврат паролей в открытом виде

`UserController::store()` возвращает `plain_password`, импорт пользователей возвращает массив `credentials`, а экспорт `логины_пароли.xlsx` доступен администратору. Это удобно для запуска, но опасно для персональных данных.

Рекомендации:

- показывать временный пароль только один раз;
- добавить срок жизни временных паролей;
- логировать факт экспорта учетных данных;
- защищать Excel-файлы паролем или отказаться от массового экспорта паролей;
- после первого входа требовать смену пароля.

### 3. Недостаточная проверка доступа к части данных

Часть маршрутов доступна всем авторизованным пользователям: `GET /results`, `GET /results/pending`, `GET /kpi/user/{user}`, рейтинги и некоторые операции с регистрациями. В контроллерах не везде есть явная проверка, что пользователь смотрит только свои данные или данные своей зоны ответственности.

Рекомендации:

- добавить Laravel Policies для User, Result, Registration, KpiScore;
- ограничить ученика только своими данными;
- ограничить учителя своими учениками/регистрациями;
- оставить глобальный доступ только директору, заместителям и администратору;
- покрыть правила доступа тестами.

### 4. Возможность загрузки результата не своим пользователем

`ResultController::upload()` принимает регистрацию из route model binding и не проверяет, что текущий пользователь является учеником этой регистрации, ответственным учителем или администратором/заместителем. Это создает риск загрузки или перезаписи результата чужой регистрации.

Рекомендации:

- проверять владельца регистрации перед загрузкой;
- запретить повторную замену подтвержденных документов без отдельного процесса;
- хранить историю замен документов.

## Высокие риски

### 5. Токен авторизации хранится в `localStorage`

Frontend хранит Sanctum Bearer token в `localStorage`. При XSS токен можно украсть и использовать до отзыва.

Рекомендации:

- перейти на httpOnly secure cookie-сессию Sanctum для SPA;
- включить CSP;
- сократить срок жизни токенов;
- отзывать старые токены при новом входе или смене пароля.

### 6. Gemini API ключ может храниться в БД без шифрования

`KpiSettingController` сохраняет `gemini_api_key` через `KpiSetting::set()`. Если значение лежит в БД открытым текстом, его можно раскрыть при дампе или SQL-доступе.

Рекомендации:

- хранить секреты в `.env` или зашифрованном хранилище;
- если ключ редактируется через UI, шифровать значение Laravel Crypt;
- не возвращать полный ключ в API, показывать только маску.

### 7. Нет ограничения попыток входа

В `AuthController::login()` не видно throttle/rate limit. Это повышает риск перебора пароля.

Рекомендации:

- добавить rate limiting на `/api/login`;
- блокировать учетную запись или вводить задержку после серии неудачных попыток;
- писать события входа в аудит-лог.

### 8. Недостаточный аудит действий администраторов

Создание пользователей, экспорт учетных данных, верификация результатов, изменение KPI и AI-настроек должны быть журналируемыми действиями.

Рекомендации:

- добавить таблицу `audit_logs`;
- фиксировать actor, действие, объект, IP, user-agent, время;
- отдельно помечать операции с персональными данными и экспортами.

## Средние риски

### 9. Проверка загружаемых файлов ограничена расширением/MIME

Загрузка допускает PDF/JPG/PNG до 10 МБ. Этого недостаточно для production-защиты от вредоносных файлов.

Рекомендации:

- хранить файлы только вне публичной директории;
- добавить антивирусную проверку или очередь проверки;
- нормализовать имена файлов;
- отдавать документы через авторизованный endpoint;
- добавить лимиты по количеству загрузок.

### 10. AI-данные сохраняются без подтверждения источников

Gemini может вернуть неточные даты и ссылки, а сервис сохраняет найденные олимпиады как активные.

Рекомендации:

- сохранять AI-результаты со статусом `pending_review`;
- требовать ручное подтверждение перед публикацией;
- валидировать URL и даты.

### 11. Недостаточная защита от утечек через Git

В проекте есть `backend/.env` и `frontend/.env`. Они уже игнорируются локальными `.gitignore`, дополнительно добавлен корневой `.gitignore`.

Рекомендации:

- перед каждым push проверять `git status`;
- не добавлять `.env`, дампы БД, Excel с паролями и пользовательские документы;
- при случайной публикации ключей сразу перевыпускать их.

## Позитивные находки

- Пароли хэшируются через Laravel Hash/bcrypt.
- API закрыт Sanctum middleware.
- Для части админских операций есть role middleware.
- Загружаемые результаты сохраняются на диск `private`.
- Используется Eloquent и валидация Laravel, что снижает риск SQL injection.
- `.env` уже исключен в `backend/.gitignore`, `frontend/.env` скрывается правилом `*.local` не полностью, поэтому корневой `.gitignore` добавлен явно.

## Приоритетный план исправлений

1. Заменить дефолтный пароль администратора и добавить обязательную смену пароля.
2. Закрыть доступ к `results`, `registrations`, `kpi/user/{user}` через Policies.
3. Проверить владельца регистрации в `ResultController::upload()`.
4. Добавить rate limit на `/api/login`.
5. Перейти с `localStorage` токена на httpOnly secure cookie или сократить срок жизни токена и включить CSP.
6. Зашифровать Gemini API ключ и маскировать его в ответах API.
7. Добавить аудит-лог действий с персональными данными.
8. Усилить обработку файлов и выдачу документов только через авторизованный endpoint.

## Вывод

Проект пригоден как базовая рабочая версия для локального тестирования и демонстрации. Перед production-запуском в школе нужно обязательно закрыть вопросы доступа к персональным данным, дефолтных учетных данных, аудита действий, защиты токенов и безопасной обработки документов.
