## Критичные проблемы безопасности

### 1. Пароли хранятся в открытом виде

Найдены:

- `users.password_plain`;
- миграция `2026_05_05_160000_add_password_plain_to_users.php`;
- `UserController::index()` делает `makeVisible('password_plain')`;
- `ProfileController::updatePassword()` записывает новый пароль в `password_plain`;
- `UsersImport` сохраняет `password_plain`;
- `UsersListExport` экспортирует `password_plain`.

Риск:

- компрометация БД раскрывает реальные пароли;
- администратор видит пароли пользователей после смены;
- Excel-экспорт может стать утечкой персональных и учетных данных.

Рекомендации:

- удалить `password_plain` из БД и кода;
- показывать временный пароль только один раз при создании/сбросе;
- после первого входа хранить только hash;
- для экспорта использовать только логин и статус `требует смены пароля`;
- добавить аудит события сброса пароля.

### 2. Sanctum token передается в query-параметре SSE

Файл:

- `backend/app/Http/Controllers/Api/ChatController.php`

Маршрут:

- `GET /api/chat/stream?token=...`

Риск:

- token может попасть в access logs, proxy logs, browser history, referer или мониторинг.

Рекомендации:

- перейти на cookie-based auth для SSE;
- либо использовать короткоживущий одноразовый stream-token;
- не передавать основной Sanctum token в URL.

### 3. Frontend хранит token в `localStorage`

Файлы:

- `frontend/src/stores/auth.js`
- `frontend/src/api/index.js`

Риск:

- при XSS злоумышленник получает bearer token.

Рекомендации:

- перейти на httpOnly secure cookies;
- добавить CSP;
- ограничить срок жизни токенов;
- отзывать старые токены при входе/смене пароля.

### 4. Вложения форума и ленты публичны

Файлы:

- `ForumController::storeMessage()`;
- `PostController::store()`;
- `ForumMessageFile`;
- `PostFile`;
- `PostPhoto`;
- `ForumMessagePhoto`.

Сейчас файлы кладутся в `public` disk и выдаются через `asset('storage/...')`.

Риск:

- материалы форума/постов доступны по прямой ссылке без проверки прав;
- закрытые темы форума могут иметь публично доступные файлы, если ссылка известна.

Рекомендации:

- хранить вложения в `private`;
- отдавать через авторизованный download endpoint;
- проверять доступ к теме/посту перед выдачей файла;
- добавить сканирование файлов и ограничения типов.

## Высокие риски доступа и целостности

### 5. `KpiController::forUser()` доступен широкому набору ролей

Маршрут:

```php
GET /api/kpi/user/{user}
```

Сейчас группа маршрута включает admin, директора, заместителей, учителей и учеников. В самом методе нет проверки, что ученик/учитель запрашивает только себя или разрешенного пользователя.

Риск:

- ученик или учитель может получить KPI другого пользователя по ID.

Рекомендации:

- разрешить полный доступ только admin/director/deputy;
- teacher/student — только свой профиль;
- добавить Policy и tests.

### 6. Nested-route ресурсы не всегда проверяют принадлежность родителю

Примеры:

- `DELETE /api/forum/{thread}/messages/{message}`;
- `DELETE /api/posts/{post}/comments/{comment}`;
- `GET/PUT/DELETE /api/prep/rooms/{room}/tests/{test}`;
- `POST /api/prep/rooms/{room}/attempts/{attempt}/grade`.

Риск:

- route model binding может загрузить `message`, `comment`, `test` или `attempt`, который не принадлежит указанному `thread`, `post` или `room`;
- при совпадении прав по пользователю или комнате можно воздействовать на чужой вложенный ресурс.

Рекомендации:

- в каждом nested-action проверять `message.thread_id === thread.id`, `comment.post_id === post.id`, `test.room_id === room.id`;
- для attempt проверять принадлежность attempt к тесту этой комнаты;
- использовать scoped bindings Laravel.

### 7. Деструктивные admin endpoints без отдельного подтверждения и audit-log

Найдены:

- `POST /api/posts/clear-all`;
- `POST /api/forum/clear-all`;
- `POST /api/olympiads/delete-all`;
- `POST /api/chat-settings/clear`.

Риск:

- один ошибочный клик или украденная admin-сессия удалит большие объемы данных;
- нет централизованного журнала кто/когда/что удалил.

Рекомендации:

- добавить audit-log;
- требовать подтверждение текстовой фразой;
- добавить soft delete/архив;
- запретить на production без отдельного флага.

### 8. Форум фильтрует права доступа в памяти

`ForumController::index()` получает все темы, затем фильтрует через collection `filter()`.

Риск:

- при росте данных будет медленно;
- легче ошибиться с утечками при будущих изменениях.

Рекомендации:

- перенести фильтр доступа в SQL query;
- добавить индексы `type`, `user_id`, `status`, `subject_id`, `olympiad_id`.
